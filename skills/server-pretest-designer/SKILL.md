# 服务器先行测试用例设计

以需求原文、确认口径和服务端实现证据为依据，先完成需求评审，再生成可映射为自动化的初版文字用例。

## 输入边界

开始前确认并读取：

- 未经改写的需求原文及关键附件；
- SunnyIsland 目标分支、相关协议、配置和服务端代码；
- 已有评审问题与人工回答；
- 相关历史用例和已有 action/assertion 能力（如存在）。

原文、代码和人工回答冲突时，人工确认的产品口径决定测试预期；代码现状只用于识别实现差异和风险。缺少关键材料时明确覆盖限制，不猜测确定结果。

## 阶段一：理解与评审

1. 从需求提取入口、角色、资格、状态、时间、数值、资产、奖励、失败、恢复、重复操作和终态。
2. 从请求入口追踪 Gate → Garden → Actor → 业务子模块 → Redis/Mongo/事件 → 响应与 Actor Diff。
3. 为重要结论记录需求位置、协议/代码符号、配置键、Actor 字段和可观察结果。
4. 优先检查会导致实现或验收不唯一的问题：主流程、状态迁移、时间边界、奖励结算、幂等、失败恢复、多人同步、持久化和可观测性。
5. 输出结构化评审问题。每题包含稳定 ID、严重度、需求位置、问题、影响和需要确认的口径；不要替产品或开发回答。
6. 进入 `waiting_review_answers` 后停止。所有阻塞问题得到人工回答前，不生成确定性初版用例。

没有有效问题时也应记录“未发现阻塞问题”和已检查范围，再进入用例设计，不能为了流程制造问题。

## 阶段二：初版用例

评审问题全部回答后：

1. 建立“需求规则/确认口径 → 风险 → 用例”的追踪关系。
2. 选择适用维度：状态、时间、网络、账号、多人、经济、权威性、配置；只展开与当前机制相关的维度。
3. 先覆盖最小服务器主流程，再覆盖边界、非法请求、重复操作、并发/乱序、断线重连、Actor 释放恢复、持久化和配置异常。
4. 为每条用例明确前置条件、业务操作、可观察预期、数据影响、清理方式、服务端证据和失败定位入口。
5. 按“模块 → 功能 → 场景 → 用例”归属，不按评审来源、测试类型或自动化能力另建业务模块。
6. 使用 [结构化用例契约](../shared-references/server-case-contract.md) 输出初版，状态保持 `draft`，不得直接进入执行中心。

## 自动化可行性

初版文字用例是先行测试契约，不是已经完成的测试代码。为每条用例标注：

- `automatable`：当前可自动化；
- `needs_action`：需要新增请求或造数 action；
- `manual_only`：暂时只能人工验证，并说明缺少的观察能力。

不要因为当前执行器没有 action 就删除高风险用例，也不要直接修改 Redis/Mongo Actor 数据来绕过正常业务链路。

## 完成条件

- 评审问题与人工答案可追溯；
- 初版预期只来自原文或已确认口径；
- 用例归入真实业务模块和功能节点；
- 文字用例尚未被误标为可执行自动化；
- 工作流进入 `waiting_case_supplements`，等待测试人员评审和补充。
