# Test Report Diagnoser

## 报告结构

报告必须先给结论，再给证据：

1. 总体状态：通过、失败或执行异常；
2. 失败阶段：连接、绑定、Actor 加载、请求、响应、Diff、持久化或断言；
3. 问题说明：用业务语言描述实际结果和期望结果；
4. 开发排查建议：关联服务端模块、协议、配置键、Actor 字段或日志关键词；
5. 执行步骤和逐条断言；
6. 原始客户端/Garden 日志与报告文件路径。

## 定位规则

- WebSocket 握手失败：检查 Gate 宿主机映射端口、`/ws` 路径、容器和网络。
- 绑定失败：检查 UID、SID、登录态和 Gate 返回错误码。
- Actor 加载超时：检查 UID 数据、Gate→Garden RPC、Redis Stream 消费组和 Actor 加载日志。
- 响应业务错误：检查请求参数、活动配置、权限、状态和幂等逻辑。
- Diff 缺失、乱序或版本不连续：检查 Actor 主循环、Diff 合并、推送顺序和断线重连。
- 断言失败：同时展示实际值、期望值、指标路径和对应需求规则，不把断言失败直接等同于服务器缺陷。

## 可读性要求

测试人员不应通过阅读原始日志才能判断问题。每个失败报告必须包含单一明确的主要原因；多个断言失败时按步骤和影响排序。事实、推断和待确认项分开标记。原始日志只作为可展开证据，不作为主要结论。
