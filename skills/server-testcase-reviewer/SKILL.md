# 服务器用例评审与迭代

将评审问题的确认口径、测试人员补充点和手工修改落实到正确的业务节点，生成终版文字用例，并保持文字用例与自动化实现的一致性。

## 必需输入

- 需求原文；
- 评审问题及每题人工回答；
- 初版结构化用例；
- 测试人员补充点或手工修改内容；
- 已有终版用例和自动化映射（再次迭代时）。

关键回答缺失、互相冲突或补充点会改变产品规则时，退回问题确认，不自行选择口径。

## 处理每条意见

1. 判断意见属于需求口径补充、覆盖遗漏、预期修正、前置条件修正、数据/环境需求还是重复内容。
2. 定位它影响的真实业务模块、功能、场景和已有用例。
3. 能扩展已有用例时，修改对应前置、步骤、预期或证据；需要独立状态组合时，在同一功能下新增用例。
4. 只有意见描述了真正的新业务能力时才创建新功能节点；不得创建“评审补充”“测试建议”“产品回答”“边界用例”或“其他”模块来收纳意见。
5. 记录处理结果：意见 ID、采纳/部分采纳/不采纳、原因、目标模块路径和受影响用例 ID。

评审问题的回答同样适用上述规则。确认口径必须落实到对应功能的用例步骤或预期中，不能只留在问题列表里，也不能复制成孤立的“评审问题用例”。

## 生成终版

1. 合并初版、确认口径和有效补充点，保留仍有效的人工用例。
2. 去重后重新检查主流程、状态、边界、失败恢复、幂等、权威数据、持久化和必要回归。
3. 按 [结构化用例契约](../shared-references/server-case-contract.md) 输出“模块 → 功能 → 场景 → 用例”树。
4. 每条终版用例通过 `source_refs` 关联需求规则、评审问题或测试建议；通过 `change_note` 简述本轮变化。
5. 给出意见处理清单和覆盖变化摘要，使测试人员能确认建议落在了哪里。
6. 终版保持 `waiting_final_approval`。测试人员确认后才允许生成或更新自动化代码。

## 手工修改与自动化同步

终版用例被双击编辑或通过其他方式修改后：

1. 先保存新的结构化文字用例版本并递增迭代号；
2. 比较前后用例的前置条件、步骤、参数、预期和断言语义；
3. 任何会影响执行行为或判断结果的变化，都将自动化状态标记为 `outdated`；
4. 测试人员重新确认终版后，再生成 action 调用、参数和 assertion；
5. 只有文字用例与自动化映射校验一致，才标记为 `ready_for_execution`。

纯说明文字修正可判定为无需重生成，但必须记录理由。不要在同一次修改中静默改写产品口径和自动化代码。

## 评审门禁

- 所有测试建议均有处理结论；
- 所有采纳意见均能定位到业务树节点和用例；
- 没有以意见来源命名的伪业务模块；
- 未确认规则未写成确定预期；
- 终版和自动化状态关系正确；
- 自动化不能覆盖的用例仍保留，并明确人工验证方式。
