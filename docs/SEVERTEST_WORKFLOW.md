# SeverTest 流程与技术实现

本文档说明 SeverTest 如何把一份服务器需求转化为可执行的先行测试。目标读者是测试人员、产品和需要配合定位问题的开发，不要求读者熟悉 Actor、Redis 或项目内部代码。

## 一、它解决什么问题

版本开始前，先对一个服务器需求做小范围验证：

```text
需求原文
  -> AI 梳理需求和服务端实现
  -> 需求评审问题
  -> 测试人员确认业务口径
  -> 初版文字用例
  -> 测试人员补充、评审和修改
  -> 终版用例
  -> 自动化代码与断言
  -> 本地/测试环境执行
  -> 可读报告和开发定位线索
```

这里的重点是先把“应该发生什么”说清楚，再决定“如何发请求和检查数据”。文字用例是测试契约，测试代码是它的执行方式。

## 二、技术实现概览

### 2.1 组件

| 组件 | 作用 |
| --- | --- |
| Web 工作台 | 上传需求、查看状态、回答问题、查看用例和执行报告 |
| Python API 服务 | 提供页面静态资源和工作流、用例、执行记录接口 |
| WorkflowStore | 将每个需求的状态和产物保存到 `requirements/.workflows/<id>/workflow.json` |
| AI Worker | 在只读环境调用 `codex exec`，生成结构化分析、评审问题和初版用例 |
| 执行器/ServerAdapter | 通过正常服务器协议造条件、发请求、读取响应和 Actor Diff |
| SunnyIsland | 被测服务器；SeverTest 不直接改它的代码或玩家存储 |

AI Worker 读取需求原文、服务器代码和 SeverTest Skill，但不能修改仓库。每个工作流有唯一 ID，页面通过 API 轮询这个 ID 的状态和耗时。

### 2.2 数据保存原则

- 需求原文原样保存在 `requirements/`，不被 AI 摘要覆盖。
- 分析、评审问题、人工答案、初版用例、补充意见和终版用例保存在同一份工作流记录中，便于追溯。
- 原始代码证据用于开发定位；测试人员看到的问题正文使用业务语言。
- 执行报告保存步骤、请求结果、断言、服务器日志和诊断结论。
- 测试工具通过正常请求造数据，不直接写 Redis、Mongo 或 Actor 文件来绕过业务链路。

## 三、从需求到执行的完整流程

### 阶段 1：上传需求

测试人员在“需求文档”页面上传 `md`、`txt`、`pdf`、`doc` 或 `docx` 文件。服务端保存原文并创建任务，状态为：

```text
需求文档已上传
```

上传成功后自动启动 AI 分析。列表会显示当前阶段和实时耗时，例如：

```text
理解需求文档中（12s）
```

### 阶段 2：AI 梳理需求和服务端实现

AI 先阅读需求，再从请求入口追踪相关的服务端流程。输出保存到“服务端逻辑梳理”，主要包括：

- 已读取的需求、协议、配置、代码和测试材料；
- 需求覆盖范围和缺失材料；
- 业务规则及其证据；
- 请求到业务模块、数据存储、响应和通知的处理流程；
- 风险、实现差异和待确认事项。

这一阶段的代码字段、函数名、Redis/Mongo 和日志关键词是给开发定位用的证据，不是要求测试人员掌握的知识。

### 阶段 3：生成需求评审问题

AI 根据分析结果提出有限数量的高价值问题，状态变为：

```text
等待测试人员回答评审问题
```

问题必须从需求和用户行为出发，通常包含：

- 什么条件下可以操作；
- 操作后用户应该看到什么结果；
- 成功、失败、重复和异常输入如何表现；
- 数据为空、达到上限或条件仍存在时如何表现；
- 哪些红点、奖励、进度或状态属于本次范围。

问题不默认询问鉴权实现、请求编码、缓存策略、存储方案、函数名或字段名。这些内容留在技术分析中，除非明确进行接口协议专项评审。

测试人员逐题回答后，答案会和问题一起保存，作为后续用例的依据。若问题措辞不合适，可点击“重新生成评审问题”，系统会清空旧问题并按当前 Skill 重新生成。

### 阶段 4：生成初版文字用例

所有评审问题回答后，工作流进入：

```text
生成初版用例中 -> 等待测试人员补充用例点
```

初版用例按真实业务树组织：

```text
业务模块
└── 业务功能
    └── 业务场景
        └── 具体用例
```

每条用例至少说明：

- 测试目标；
- 前置条件；
- 业务操作步骤；
- 测试人员可观察的预期结果；
- 数据影响和清理方式；
- 来源引用（需求、评审问题或补充意见）；
- 服务端证据和自动化可行性。

初版的 `assertions` 保持为空。因为此时业务口径刚闭合，机器断言还需要经过测试人员补充和终版确认。

### 阶段 5：补充、评审和生成终版

测试人员在初版用例基础上补充遗漏场景，例如重复请求、跨状态、断线重连、Actor 释放恢复或配置异常。补充内容必须归入已有业务模块和功能节点，不单独创建“测试建议”“边界用例”等模块。

后续状态为：

```text
等待测试人员补充用例点
  -> 生成终版用例中
  -> 等待测试人员确认终版用例
```

测试人员可以在终版确认前双击或编辑用例文字。修改用例的前置条件、步骤、预期或断言后，已有自动化会标记为 `outdated`，需要重新生成，避免文字用例和测试代码不一致。

### 阶段 6：生成自动化并进入执行中心

确认终版用例后，系统再生成测试代码和断言：

```text
生成测试代码和断言中 -> 可以执行
```

执行中心只接收已经确认、自动化状态为 `ready` 的终版用例。初版用例不会直接出现在可执行列表中，避免在需求口径未确认时误跑测试。

### 阶段 7：执行和报告

测试人员在“执行中心”填写本地环境参数并选择一个或多个用例。执行器通常按以下顺序工作：

```text
准备专用账号/SID
  -> 通过正常请求造数据
  -> 发起目标业务请求
  -> 读取响应和 Actor Diff
  -> 必要时检查 Redis/Mongo 结果和服务器日志
  -> 执行业务断言
  -> 保存结构化报告
```

支持单条和批量执行。报告优先展示测试人员能读懂的结论：

- 是否通过；
- 失败发生在哪个业务步骤；
- 实际结果与预期结果的差异；
- 可能的问题范围；
- 给开发的代码、日志和数据排查线索。

原始客户端和服务器日志作为详情折叠展示，不代替 QA 结论。

## 四、工作流状态速查

| 状态 | 含义 | 谁负责下一步 |
| --- | --- | --- |
| `uploaded` | 原文已保存，尚未开始分析 | AI Worker |
| `understanding_requirement` | 正在理解需求和读取代码 | AI Worker |
| `reviewing_requirement` | 正在生成需求评审问题 | AI Worker |
| `waiting_review_answers` | 等待测试人员确认业务口径 | 测试人员 |
| `generating_draft_cases` | 正在生成初版文字用例 | AI Worker |
| `waiting_case_supplements` | 等待测试人员补充和评审初版 | 测试人员 |
| `generating_final_cases` | 正在生成终版用例 | AI Worker |
| `waiting_final_approval` | 等待测试人员确认终版 | 测试人员 |
| `generating_automation` | 正在生成测试代码和断言 | AI Worker |
| `ready_for_execution` | 用例和自动化均已准备好 | 测试人员 |
| `failed` | 某阶段处理失败 | 测试人员重试或定位原因 |

## 五、当前边界和使用建议

1. 第一次接入新需求时，先选一个小功能跑通“分析 → 评审 → 初版用例”，确认问题语言和用例归属符合团队习惯。
2. 评审问题回答的是产品/需求口径，不是让测试人员替开发决定 Redis、Actor 或接口实现方案。
3. 服务器代码现状与需求不一致时，先记录为风险；最终预期以人工确认的产品口径为准。
4. 自动化失败时先看报告中的业务定位，再展开原始日志；不要只根据进程退出码判断缺陷位置。
5. 涉及真实测试服、账号数据或批量执行前，确认环境、UID、Gate 地址和容器网络，避免把演示数据写入错误环境。

## 六、常用入口

启动本地工作台：

```bash
PYTHONPATH=src python3 -m severtest.server
```

浏览器打开：

```text
http://127.0.0.1:8088/
```

健康检查：

```bash
curl http://127.0.0.1:8088/health
```
